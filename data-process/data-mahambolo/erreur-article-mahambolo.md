Le concept du bug identifié
En comparant le CSV source, le SQL généré et le rapport d'erreurs, j'ai pu isoler la logique exacte du problème : le script de génération n'a pas conservé l'ordre des lignes du CSV pour chaque article — il a trié les unités par qtunite (quantité) croissante, au lieu de respecter l'ordre d'apparition dans la source. Résultat : les noms d'unités (designationunite) se retrouvent associés au mauvais niveau hiérarchique, alors que les couples (quantité, poids) restent cohérents entre eux (juste mal étiquetés).

Preuve avec 3 exemples
Exemple 1 — 70/19
CSV (ordre d'apparition) : KG → BOITE (qty=5) → CARTON (qty=4)
SQL généré : niveau0=KG(1) → niveau1=CARTON(qt=4) → niveau2=BOITE(qt=5)

→ Les niveaux 1 et 2 ont été inversés car 4 (CARTON) < 5 (BOITE). Le script a trié par quantité croissante au lieu de garder l'ordre CSV.

Exemple 2 — AGHARBATTI SEVEN WONDER FLOWES
CSV : BOITE (qty=12) → PAQUET (qty=1)
SQL : niveau0=PAQUET(qt=1) → niveau1=BOITE(qt=12)

→ Même phénomène : PAQUET (qty=1) passe devant BOITE (qty=12) car 1 < 12.

Exemple 3 — BENNY
CSV : PIECE(1) → BOITE(qty=42) → CARTON(qty=8)
SQL : niveau0=PIECE(1) → niveau1=CARTON(qt=8) → niveau2=BOITE(qt=42)

→ Le niveau 0 (unité de base, toujours qty=1) reste stable, mais les niveaux ≥1 sont systématiquement réordonnés par quantité croissante.

Cause probable
L'algorithme SQL trie (implicitement ou explicitement) les lignes d'unités par la valeur numérique de qtunite avant de leur assigner un niveau, alors qu'il devrait simplement numéroter les niveaux dans l'ordre exact des lignes du CSV (niveau = position de la ligne - 1 pour chaque CODE/article).
